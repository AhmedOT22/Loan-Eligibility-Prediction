# Modelling decisions and release handling

## Problem and target

Predict the supplied CSV's `Loan_Approved` Y/N label from eleven raw features. This demonstrates supervised learning on a historical label, not a lender decision engine. The positive class is Y; a false positive means predicting Y when the recorded label is N. The data does not establish why an individual label was assigned.

## Current serving release

`models/serving/v1` contains complete Logistic Regression and Random Forest pipelines plus a shared manifest. Each pipeline owns numeric median imputation/MinMax scaling, categorical mode imputation/one-hot encoding, and its classifier. Training uses only the seed-42 stratified 80% partition. There is no full-data refit, threshold optimization, or calibration.

The manifest records input SHA-256, raw feature order, fitted category vocabularies, target meaning, split settings/counts, build timestamp, package versions, model checksums, and aggregate holdout metrics. No applicant labels, scores, identifiers, or split indices are exported by the release builder. Artifact files contain fitted model parameters and preprocessing, not a row-level report.

The app checks format, schema, checksum, and exact scikit-learn version before loading. It also checks the fitted pipeline's classes, feature order, and category vocabularies against the manifest. These checks detect mismatched release files; they do not authenticate an untrusted manifest or make malicious pickle files safe.

The form adapter requires complete, supported raw inputs. Although the pipeline's encoder supports unknown categories for candidate experiments, the app rejects them instead of returning a score from an all-zero category encoding. It also rejects malformed fields, nonfinite/negative numeric values, nonpositive loan amount/term, and credit-history values other than 0 or 1. No user-input statistics are fitted and no submitted values or scores are logged by the app.

## Build, promote, and roll back

```bash
# Writes a new directory; refuses to replace existing files:
python build_serving.py --output reports/latest/serving-candidate
```

The builder writes artifacts and metadata into a temporary directory, reloads each pipeline, and compares its aggregate metrics before renaming the complete release into place. It never publishes the local row diagnostics generated by `train_model.py`.

Before promotion, compare metrics with the existing release and the baseline; inspect schema, package versions, and provenance; run the application tests against the candidate. Copy the verified directory to a new version under `models/serving/`, update `SERVING_DIR` in `src/models/serving.py`, and commit those changes together. Do not replace old files by renaming individual encoded estimators into pipeline filenames. A dependency upgrade needs rebuilt and tested artifacts; editing version strings is not a compatibility fix.

For a later release rollback, restore the previous `SERVING_DIR` and compatible code/dependencies in a new commit. Never rewrite published history. The migration from the old encoded app can be reverted as a complete commit if necessary. Its earlier source is preserved at `e13455b3379a7a70c354b2d4f79d069f16314561`, and the original `models/*_model.pkl`/`models/scaler.pkl` files remain untouched. The current app deliberately has no automatic legacy fallback, because that would silently change the model and invalidate the displayed evaluation.

## Legacy path

The old preparation learned missing-value/scaling statistics before splitting. Repairing its inference adapter could not undo that history. The old accuracy JSON files therefore describe legacy evaluations and are not used in the current app. Legacy helpers remain for compatibility and are covered by regression checks; the main training workflow and serving release do not call whole-dataset preparation.

## Evaluation choices

- Reserve a stratified 20% holdout using seed 42 before fitting preprocessing. This is random, not temporal or external validation.
- Compare fixed classifiers against a majority baseline. No parameter search uses the holdout.
- Run repeated five-fold CV on only the remaining 80%, refitting the full pipeline in each fold.
- Report accuracy, precision, recall, specificity, ROC AUC, average precision, Brier score, and confusion matrices. High positive recall alone can hide poor negative-class performance.
- Pool one repeat for threshold diagnostics, avoiding counting every row three times. Threshold 0.5 stays fixed; choosing a decision threshold requires a defined objective and separate validation.
- Treat fold SD descriptively. Overlapping training folds are not independent experimental replications.

Logistic Regression scales features because its coefficients depend on their scale. Random Forest shares the preparation contract for simplicity, although trees do not require MinMax scaling. Cross-validation does not establish a universal winner: Logistic Regression leads on mean accuracy/Brier score, Random Forest slightly on ROC AUC.

## Remaining limits

Source, collection period, geography, currency, and amount units are unverified. A row may not be an independent applicant; grouping and repeat applications have not been established. Random splits may remain optimistic despite correct preparation.

Gender and marital status reproduce the supplied task. Their presence is not an endorsement for real financial decisions. No fairness, legal suitability, calibration, or production-readiness claim is supported. Optional future research includes calibration, explicit threshold costs, and subgroup analysis with adequate sample sizes. These would be new experiments, not automatic release improvements.

The repository overhaul aligns code, preparation, evaluation, and serving. It does not resolve missing provenance or establish a verified hosted deployment. Existing figures are genuine evaluation outputs rather than screenshots of a live service.
